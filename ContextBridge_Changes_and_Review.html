4. Changes to the shared engine

4.1 Capture and migration

The watcher is explicitly started rather than silently launched. It polls metadata and records batches after quiet periods or a batch-window limit. Repeated saves coalesce. Own-output paths, dependency/build/cache folders, secret files and ignored files are excluded. Automatic change records store paths and numeric summaries rather than source contents.

Migration from .context/ to .contextbridge/ copies data and retains the legacy folder. Current storage takes precedence when valid databases exist in both. This improves safety, although maintaining legacy compatibility increases implementation complexity. Polling can miss several intermediate saves; it is not a complete edit-by-edit audit trail.

4.2 Handoff quality and conversation imports

The handoff reserves room for essential sections, defaults to roughly 2,000 tokens and ranks source ahead of tests. Tests are aggregated, source attribution can remain unknown, same-agent transfers warn, and the most recent session receives more detail than older work. Todo states allow old work to be resolved, dismissed or superseded.

Chat imports parse recognizable user/assistant turns and preserve chronology. Goals are condensed; completed claims become neutral statements; explicit follow-ups are separated from pleasantries. Imports redact secrets and remove noise. These are heuristic parsers: unusual transcript formats can still reduce quality. Short or turnless inputs should be treated cautiously rather than assumed to be reliable conversations.

4.3 Offline summaries

Summaries can use README text, package metadata, languages, file/folder inventory, entry points, symbols, imports and Git history without requiring existing logs. Content-hash caches avoid repeated analysis of unchanged material. Sparse-note handoffs can include “What each part does.”

Offline does not mean equally descriptive in every language. The current sample handoff still emitted statements such as “Defines Card” and “Imports express.” Those are grounded, but they do not explain the file's role well. The browser graph handles this more honestly with “Not explained yet.”

4.4 Providers, grounding and quotas

Model work is bounded and optional. Code is ranked and chunked rather than sent as a whole repository. Structured output is validated, invalid output can retry once, and explanations are stored separately from grounded purpose fields. The provider layer includes reasoning-model handling, selected-model probes and endpoint/model error details.

Rate-limit headers, backoff and cooldowns inform pacing. Partial results are cached so rerunning can resume. Explain project uses visible request and reserved-token budgets and is not restricted to the regular summarizer's eight-file selection. These controls reduce waste but do not guarantee that a provider will accept every request. Reserved tokens are an estimate, not a billing meter.

Identifier validation rejects invented file/function/class references; it does not prove every sentence is semantically correct. AI-written labels remain important even when validation passes.

7. What got worse, remains incomplete, or needs correction

7.1 Confirmed correctness bug: failed commands look successful

Reproduced: running python3 -c 'raise SystemExit(1)' in the isolated sample produced exit code 1, unknown test counts and an unrecognized runner. The history UI displayed “✓ passed · 0 passed”. The handoff correctly reported exit 1 and an open problem, so two screens disagreed.

ChangesTestsTab.jsx treats a missing failure count as success. It should use the exit status and recognition status: nonzero exit means command failed; unrecognized counts mean counts unavailable. Do not display “0 passed” for unknown counts. History also expects started_at/finished_at, while the API returns ran_at, so the recorded timestamp rendered as a dash.

7.2 Graph readability is still below the requested standard

The cream canvas is better and there was no observed overlap in the small fixture. However, six overview boxes were scaled small enough that their text was difficult to read at normal viewing size. Excess canvas space and an automatic fit transform reduce usefulness. Improve the initial layout/zoom, preserve a readable minimum text size, and allow scrolling/panning rather than shrinking every card to fit.

7.3 Sidebar contrast is inconsistent

The project-switching helper paragraph was visibly low contrast on burgundy. The generic .hint rule applies the light-surface muted text color and overrides the intended sidebar color. Scope that styling or explicitly override it in dark navigation. The current project path also wraps heavily in the narrow sidebar.

7.4 Explanation error recovery is weak

With offline mode selected, Explain project showed a dialog instructing the user to configure a provider, with only Retry visible. Escape dismisses it, so it is not a permanent trap. It still needs a visible Close action and a direct Open Settings action. Retrying without changing the provider cannot resolve the error.

7.5 Browser setup and project switching add friction

The React dashboard currently needs dependencies, a build, a running local server and a session-token URL. For a developer this is manageable; compared with the documented desktop launcher it is a step backward in installation-to-use convenience. Switching projects requires stopping and restarting the server with another repository path. Showing that limitation honestly is an improvement; solving it remains future work.

7.6 Importing files is less convenient than a picker

Chat bridge accepts a typed project-relative path for text, Markdown or PDF. This avoids unrestricted file access, but users must know the path and place the file inside the project. A deliberate file-picker/upload flow would be easier; keep explicit selection and the existing size/privacy controls.

7.7 Handoff explanations remain uneven

Current offline output can repeat “Defines …” descriptions across What each part does and Files to read first. This is accurate but low value for beginners and can waste the budget. Prefer documentation-backed descriptions, distinguish the purpose of the two sections, and avoid duplicated lists. This was observed in a tiny sparsely documented sample; it is not a claim that all repository handoffs have equally weak descriptions.

7.8 More interfaces mean more maintenance

CLI, Qt, HTTP API, MCP and React now coexist. Shared services reduce duplication, but every new workflow must still be represented consistently in several clients. Separate limits and data contracts can drift, as the history timestamp mismatch demonstrates. This is an architectural tradeoff, not a reason to discard the rebuild.

7.9 Documentation has drifted

The README combines old Step 6 notes and newer dashboard instructions. An older section says the API is deferred and every route requires authentication, while the dashboard must intentionally serve its UI assets before authentication and authenticate API calls. Consolidate the current contract: public local UI shell/assets; token-protected API; token carried in the URL fragment and sent as an Authorization header. Clearly label older milestone notes as historical.

8. How the current app works

  1. Launch: cb serve chooses one repository, creates a random session token and starts the loopback server.
  2. Load UI: the browser receives the built React assets under /ui/. It obtains the token from the launch fragment or token form and retains it in browser local storage.
  3. Authenticate: API requests attach Authorization: Bearer …. Restarting the server changes the token.
  4. Read project state: FastAPI calls shared Python services for notes, tasks, changes, Git history, summaries and graph JSON. Project records live in SQLite.
  5. Render: React renders the service data; React Flow displays graph nodes and edges. It does not independently invent the dependency graph.
  6. Run explicit work: user actions start command jobs or explanation jobs. Status endpoints provide output/progress rather than making page opening trigger those jobs.
  7. Use a model only when requested: explanations or handoff polishing use the configured provider, privacy controls, redaction, pacing and caches. Default handoffs remain deterministic.
  8. Transfer context: a preview can be copied/exported or written using an agent adapter. Task import saves database rows; it does not create a Git commit.

This separation is the main technical improvement: graph analysis and context rules stay in Python, while rendering can evolve independently. It also leaves a clearer path to a later desktop wrapper, but the presence of React alone does not mean a packaged Tauri application already exists.

The four Python skips were two cases requiring cb on PATH, one requiring pytest on PATH and one optional ChromaDB import. The warning concerned Starlette/httpx test-client deprecation. These are not four passing tests and should remain visible in release reporting.

No live Groq call or paid provider request was used for the manual review. Real model latency, quotas and explanation quality therefore remain unverified for this browser session. The review did not recheck a large Flutter project or every Qt workflow.

Why a green suite still missed a real defect

Tests covered many happy paths, but the history UI's unrecognized-command/nonzero-exit combination was not protected sufficiently. Add regression coverage based on exit code, unknown counts, missing timestamps and differing payload shapes. The result should be “command failed; test counts unavailable,” not a green pass.

11. Running the current version

Initial setup and build

cd /Users/vasysta/Documents/ContextBridge
uv sync --extra api
npm --prefix frontend ci
npm --prefix frontend run build
uv run cb serve

Open the complete URL printed by the server, including #token=…. Keep the terminal running. Rebuild after frontend source changes; normal later launches only need uv run cb serve.

Switch projects

Press Ctrl+C in the running server terminal, then start it for the other project and open the newly printed URL:

uv run cb --repo "/absolute/path/to/other-project" serve

The active repository determines its local records. The provider configuration can be influenced by global and project settings; project separation does not imply every setting is independent.

Useful validation commands

.venv/bin/python -m pytest -q
.venv/bin/python -m ruff check contextbridge tests
.venv/bin/python -m mypy contextbridge
npm --prefix frontend test
npm --prefix frontend run build
npm --prefix frontend run test:browser

Browser tests require a usable Playwright browser installation. Environment launch failures should be reported separately from application assertion failures.

Against the first React prototype: clearly better in workflow completeness, theme continuity, production loading, graph interaction and goal integration.

Against the earlier desktop experience: stronger browser-facing structure and reuse of an improved engine, but not yet an unqualified usability upgrade. Launching and switching projects require more manual work, and some feedback is still misleading.

Product maturity: a useful, substantially improved prototype with a sound shared-engine direction. Fix the confirmed correctness issue before treating test status as trustworthy. Finish readability and recovery paths before treating the React frontend as a polished desktop replacement.
